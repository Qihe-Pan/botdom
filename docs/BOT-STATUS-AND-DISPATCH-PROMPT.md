# Botdom 群协作：状态与调度检查任务

请主管协调员工，优先修复真实调度、消息投递和并行执行，再统一界面状态。每项报告代码位置、失败触发条件、修复、隔离测试及尚未验收的内容；主管认可不等于用户验收。

## 状态契约

- **空闲**：当前群与其他会话均无活动执行。**思考中**：本群执行已启动，等待模型生成。**工作中**：本群执行正在调用工具或产生输出。不能仅从旧消息推断当前活动。
- **排队**：这一具体派工尚未开始，说明等待当前执行、同一员工的其他会话或前序派工；同一员工同时工作和另有排队任务时，区分两个 execution/assignment。
- **等待用户**：实际存在待回答的问题或审批，注明对应员工和执行；回答必须回到同一个执行。**其他会话工作中**：员工在别处忙，不能冒充本群正在执行。
- **停止中 / 已暂停**：停止已请求但清理尚未结束时显示停止中；清理完成后更新为真实暂停或空闲。**失败 / 受阻**：显示已确认的原因，如额度不足；普通工具单次失败不等于整轮失败。
- 任务板分别表达待安排、进行中、已回报、主管认可、退回、受阻、用户验收和取消。只有用户能标记验收；回报、主管认可和验收不能混为一谈。
- 群顶成员卡、正在工作区、队列、任务板、流转动画及刷新重连后的快照依据同一执行事实及时更新；未知状态保持未知，不能编造工作、任务名或成功。

## 必查流程

1. 用户在员工工作时 @本群主管：明确接收人与消息状态，不能把指名主管的话静默交给当前员工当作已处理；保证有明确排队/回复，解决用户长时间等不到主管的问题。
2. 插话、队首变化、重复点击、引擎结束和重连交错时，消息不得丢失、重复执行或凭不确定回执声称已送达；不同 sender/目标的消息不得混入错误执行。
3. 两名员工实际并行，独立执行 ID、流式正文、工具、审批/问题、状态和结果；相同 requestId 不得使回答或审批送错员工。完成、失败和全部停止各有正确收尾，主管在需要时汇总一次。
4. 同一员工当前运行一项、后续排队另一项时不合并掉身份，不显示虚假的 A 等 B、B 等 A；跨群和私聊也不得串状态。
5. 排序和优先级以用户保存的意图影响后续派工，但不得抢占在跑的任务、改变真实执行状态或覆盖用户验收。
6. 员工仍在执行时，主管跟进要保持主管互斥、引用对应用户消息，并保留原 Goal 的 runId、目标卡和任务板；不能将普通状态询问另起一个遮蔽原目标的 Goal。用户新增指令要以消息 ID 持久关联原 Goal，明确显示等待或已处理，在后续调度中实际消费，不能只依赖可能截断的聊天历史。覆盖多条补充、员工同时完成、停止、重启、重复投递和原任务只汇总一次；不得把未落实的指令说成已派工。
   每次派工必须明确关联它实际承接的补充消息 ID，并在对应员工的执行真实开始后记录对应 executionId；无关任务启动不能消耗其他消息。员工启动后失败、超时或停止时，要准确保留未完成状态，不能因曾派工就认定要求已经落实。主管以普通文本答复时也不得绕过待处理检查，更不能在要求仍等待处理时把 Goal 标为完成。至少验证两条要求分别交给不同员工、无关任务启动、员工失败和普通文本回复等场景。

只在隔离副本、独立临时数据/端口和假引擎做修改性验证；用户明确要求运行新增用例，先跑受影响的逻辑与集成测试，再进行隔离 Electron 桌面验收。不得把 DOM 测试冒充桌面验收。并行未通过身份隔离、停止与授权验证前，不得说可以安全上线。测试完成后清理自己创建的临时进程和数据。
